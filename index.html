    Start Here: What You're Building and How to Read This Guide

    Your organization runs many Red Hat Enterprise Linux (RHEL) servers on a network with no internet connection. That's called an air-gapped or disconnected network. Those servers still need software and updates. Red Hat Satellite is the answer: it's a private "app store and update center" that lives inside your network. You load software into Satellite by hand (from DVDs and approved transfer media), and every other server gets its software from Satellite instead of the internet.

    In this guide you build that Satellite server from nothing: an empty virtual machine, the operating system, the network, the security hardening, and finally Satellite itself.

    💡 Why is this so careful?

    This server is built to DISA STIG rules. STIGs are the U.S. Department of Defense's security checklists, and they decide things like how disks are split up, how passwords work, and which ports can be open. Many steps look "extra." They exist because an auditor will check them.

    Flags: when to use one dash (-) or two (--)

    Flags are the extra settings after a command. You'll see two styles, and they usually do the same job. One is short and quick to type; the other is a full word that's easier to read.

    🔒 The fixed rules
    1. One dash + one letter = a short flag. ls -a means "list all files."
    2. Two dashes + a word = a long flag. ls --all is the exact same thing, spelled out.
    3. Short flags can be stacked behind one dash. ss -tlnp is the same as ss -t -l -n -p. Long flags can never be stacked; each one gets its own --: ss --tcp --listening --numeric --processes.
    4. Some flags need a value after them. Short: a space, then the value: findmnt -o TARGET. Long: an = or a space: findmnt --output=TARGET.
    5. Two dashes all alone (--) means "no more flags after this." Everything after it is treated as a name, even if it starts with a dash.
    6. A letter only means something inside its own command. -p is a good example. It means something different in almost every command (see the table below). Never assume. Check the command's help.
    🔀 Which one should you use?
    • Typing at the terminal: short flags. They're faster, and it's what you'll see in most examples.
    • Writing scripts, Ansible playbooks, or documentation: long flags. Someone reading --human-readable six months from now knows what it does; -h makes them look it up.
    • Both work the same. It's a readability choice, not a right-or-wrong choice.

    The two-dash stop sign: -- by itself

    Sometimes a file name starts with a dash, and the command thinks it's a flag. Putting -- in front says "flags are over; what follows is just a name."

    bash — exampletouch -- -test.txt
ls -l -- -test.txt
rm -- -test.txt
    touch -- -test.txt
    Create an empty file literally named -test.txt. Without --, touch would complain that -t is a flag it wasn't expecting like that.
    ls -l -- -test.txt
    -l is a real flag (before the stop sign). -test.txt comes after it, so it's a file name.
    rm -- -test.txt
    Delete it, same idea.
    📣 Commands that break the rule
    • One dash + a whole word: some older tools do this. find /var -type f -name '*.rpm' (not --type), and openssl req -new -key cockpit.key -out cockpit.csr. For these, -name is one flag, not -n -a -m -e.
    • No dashes at all: subcommands are plain words. systemctl restart, nmcli connection modify, hammer repository list. The words come first; flags come after.
    • PowerShell (Windows): always one dash + a word, and capital letters don't matter: Test-NetConnection -ComputerName sat01 -Port 9091.

    💡 What does cat > file <<'EOF' really mean? (You'll use it a lot.)

    Many steps need you to create a small settings file. The usual way is to open a text editor, but editors are clumsy inside the vSphere console. This trick lets you type the whole file right in the terminal instead:

    examplecat > /etc/example.conf <<'EOF'
line one of the file
line two of the file
EOF

    Read it left to right like a sentence:

    1. cat means "take what I give you and hand it back out." By itself it just repeats text.
    2. > /etc/example.conf means "don't show that text on screen. Put it into this file instead." If the file already exists, it is replaced.
    3. << means "the text I'm giving you is coming right here, on the next lines, not from another file." This is called a here-document ("the input is here").
    4. EOF is the stop word. It stands for "End Of File." It tells the shell: "keep reading lines until you see a line that says only EOF." The stop word isn't saved into the file. You could use any word, like DONE. EOF is just the tradition, so everyone recognizes it.
    5. The quotes around 'EOF' mean "copy every line exactly." Without them, the shell would try to "fill in" anything starting with $ (it would think $HOME is a variable and swap in your home folder). With the quotes, what you type is what goes in the file.

    In one sentence: "Create this file, and here is everything that goes in it, up to the word EOF."

    📣 The final EOF line must be alone on its line, with no spaces before or after it. If the terminal shows a > prompt and seems stuck, it's still waiting for that line. Type EOF and press Enter.

    Step 1

    Create the Empty VM in vSphere

    First you build the "computer": an empty VM with the right amount of processing power, memory, and disks. Nothing is installed yet. Think of it as buying the hardware.

    💡 Why two separate disks?

    The small disk (200 GB) holds only the operating system. The big disk (2 TB) holds Satellite's software library, which keeps growing. If the library ever fills its disk, the operating system is on a different disk, so the server can still boot and you can still log in to fix it. It's like keeping your kitchen and your warehouse in separate buildings.

    Step 2

    Test That the VM Boots From the RHEL DVD

    Before installing anything, make sure the right DVD is in the drive and it works. This takes two minutes and catches the most common setup mistake: the wrong ISO.

    1. Select the VM → Launch Remote Console (or Launch Web Console). This is your screen and keyboard for the VM.
    2. Power on the VM.
    3. You should see a menu with Install Red Hat Enterprise Linux 9.8.
    4. Choose it and wait for the installer's Installation Summary screen. (The installer is called Anaconda.) Don't start installing yet.
    5. Look at Installation Source. It should say Local media with no warning. That means the installer found all the software on the DVD.
    6. Power off the VM from vSphere.
    🔧 If this happens
    • You see a Satellite screen or a "rescue" menu → the Satellite ISO is in the drive. It can't boot a computer. Swap it for rhel-9.8-x86_64-dvd.iso.
    • Installation Source shows an error → you used the small "boot" ISO, which has no software on it. Use the full DVD ISO.
    ✔ Checkpoint 2
    1. The installer reached Installation Summary, the source said "Local media," and the network was still unplugged.
    2. Screenshot saved for your portfolio.
    Step 3

    Install RHEL 9.8: FIPS, STIG, and Separate Partitions

    Now you install the operating system. Three security choices happen here, and they're hard to add later. FIPS means only government-approved encryption. STIG means the DoD security checklist is applied automatically. Separate partitions means each important folder gets its own fenced-off space on the disk.

    💡 Why does STIG want separate partitions?

    Picture one big room where everything is stored. If one pile grows out of control, like logs from a noisy program, it fills the whole room and the system crashes. Separate partitions are walls: each folder gets its own room with a fixed size. If the log room fills up, the operating system's room is untouched.

    Walls also let you put rules on each room, called mount options:

    • noexec: "nothing in this room may run as a program." It stops an attacker from dropping a program into a temp folder and running it.
    • nosuid: "ignore special 'run as admin' markers on files here." It blocks a common privilege trick.
    • nodev: "no device files here." Device files are special files that talk directly to hardware.

    Those rules can only be set on a whole partition, never on a single folder. That's why STIG requires the walls.

    3a. Start the installer in FIPS mode

    1. Power on the VM. At the menu, highlight Install Red Hat Enterprise Linux 9.8 and press e ("edit this boot option").
    2. Find the line that starts with linuxefi or linux. Move to the end of that line and type a space, then fips=1.
    3. Press Ctrl+X to start with that change.
    💡 What is FIPS, and why turn it on this early?

    FIPS 140 is a U.S. government standard that lists which encryption methods are approved. fips=1 tells the installer "use only approved encryption from the first second." During install, the system creates its own secret keys (for example, SSH keys that prove the server's identity). If FIPS is already on, those keys are made the approved way. Turning FIPS on later would leave keys that were made the unapproved way. Also, since RHEL 9.6, picking the STIG profile no longer turns FIPS on for you, so you must do this yourself.

    3b. Software and security profile

    1. Software Selection → Server (no desktop) or Minimal Install. Add nothing extra. Less software means fewer things to patch and secure.
    2. Security Profile → select DISA STIG for Red Hat Enterprise Linux 9 → Select profile → Done. The installer will now apply hundreds of security settings for you.
    3. Leave Network & Host Name alone. The network is unplugged on purpose.
    4. Time & Date: pick your time zone. The time server comes in Step 4.

    3c. Split up the disks

    This is the biggest part of the install. You'll use LVM (Logical Volume Manager). LVM pools a disk's space into a volume group, then carves that pool into logical volumes (the "rooms"). The big advantage: you can make a room bigger later without reinstalling.

    🔒 Always true for the disk layout
    • The 200 GB disk gets its own pool named rhel (operating system). The 2 TB disk gets its own pool named data (Satellite). The two never mix.
    • These folders must each get their own room (STIG): /boot, /boot/efi, /home, /tmp, /var, /var/log, /var/log/audit, /var/tmp.
    • Satellite's two heaviest folders also get their own rooms: /var/lib/pulp (the software library) and /var/lib/pgsql (the database).
    • Leave some of the data pool unused, so you have room to grow later.

    3d. Accounts

    1. Root Password: set the approved root password.
    2. User Creation: create your admin account and check Make this user administrator (this lets it use sudo).

    The vSphere console sends which key you pressed, not which letter you meant. If your computer's keyboard layout doesn't match what the VM expects, symbols like @ # $ \ | can come out different. Password typing is hidden, so you'd never see it, and 3 misses locks you out.

    For your first login, pick a password (STIG still needs 15+ characters with upper, lower, a number, and a symbol) whose symbol you've tested in the console first. Safe bets are - and .. Change it later from SSH or Cockpit if you like.

    3e. Install and first boot

    1. Check that every item on the summary is ready → Begin Installation. This is when the disks are actually written.

    6g. Lab vs. production: what changes when DoD issues the certificate

    In this lab, your own internal CA (AD CS) signs the certificate. In production on a DoD network, you don't sign it yourself. You send the request to the DoD PKI (Public Key Infrastructure, the DoD's official certificate system), and it sends back an official DoD certificate. The steps on the server look almost the same. What changes is who signs, who is trusted, and how much paperwork is involved.

    💡 Three levels of ID card
    • Self-signed (Cockpit's default): the server made its own ID card. Like writing your own name on a sticky note. Nobody has a reason to trust it, so browsers warn.
    • Internal CA (this lab): your organization's own office signs it. Trusted only by computers you told to trust that office. Fine for a lab or a small enclave.
    • DoD PKI (production): the Department of Defense's official office signs it. DoD computers already trust the DoD root CAs (they're installed by the DoD InstallRoot tool or by group policy), so every DoD workstation trusts your server with no extra setup. Auditors expect this on DoD systems.

    When something doesn't go to plan

    Troubleshooting & Fixes

    Problems met during real builds, with what you see, why it happens, the fix, and how to confirm it worked. Search by error text or command.

    🔒 The golden rule: ask before you change

    Never guess. Let the server tell you what's wrong first, using commands that only look and never change anything. Always check from the inside out: the service → SELinux → firewall → network → your computer. Stop at the first thing that fails. That's your problem.

    • journalctl -u <service> -b --no-pager | tail -50: a service's log. -u = which service ("unit"), -b = only since the last boot, --no-pager = print it all at once instead of one screen at a time, tail -50 = only the last 50 lines.
    • tail -f /var/log/secure: watch login attempts live. -f = "follow," keep showing new lines as they happen. Press Ctrl+C to stop.
    • ausearch -m AVC -ts recent: what SELinux blocked. -m AVC = the "access denied" message type, -ts recent = from the last 10 minutes.
    • df -h and vgs: how full each room is (-h = readable sizes) vs. how much unused space is left in each disk pool.
    • klist -kte /etc/krb5.keytab: (only if joined to Active Directory) the exact Kerberos identities this server holds. -k = read the keytab file, -t = show dates, -e = show encryption types.

    The password is right, but login keeps failing

    Step 3 onward · logins · faillock · STIG
    What you see
    "Authentication failed" even with the right password. Resetting the password as root doesn't help.
    Why
    STIG turns on pam_faillock, a lockout counter. After 3 bad tries it locks the account, and it usually never unlocks by itself. The counter is stored separately from the password, so changing the password doesn't reset it. The login prompt still appears on purpose, so an attacker can't tell the account is locked.
    Fix
    From a root session (the vSphere console): 
    bashfaillock --user 
faillock --user  --reset
grep -E '^(deny|unlock_time|dir|even_deny_root)' /etc/security/faillock.conf
    faillock
    The tool that reads and clears the lockout counter.
    --user NAME
    Show that user's failed attempts.
    --reset
    Clear the counter, which unlocks the account.
    grep -E '^(…)'
    Show the lockout settings: how many tries (deny), the auto-unlock time (unlock_time, where 0 = never), where the counter is stored (dir), and whether root can be locked too (even_deny_root).
    Check it
    faillock --user <user> shows no entries, and login works.
    Prevent it
    Test symbols in the console before using them in a password. See console mistypes characters.

    Root is locked out too

    logins · emergency recovery
    What you see
    Even root can't log in on the console after bad attempts.
    Why
    STIG often sets even_deny_root, which means root gets locked too.
    Fix
    You'll use the boot menu to get in before the lock is checked:
    1. Reboot. At the boot menu press e (edit). STIG protects this with a boot-menu (GRUB) password, so have it ready.
    2. On the linux line, add rd.break at the end, then press Ctrl+X. rd.break means "stop early in startup and give me an emergency root shell."
    3. mount -o remount,rw /sysroot: the real system is connected at /sysroot but read-only. remount,rw makes it writable.
    4. chroot /sysroot: "change root," step inside the real system so your commands affect it.
    5. faillock --user root --reset: clear root's counter.
    6. touch /.autorelabel: touch creates an empty file. This one tells SELinux to re-check every file's label on the next boot, because you changed things while SELinux wasn't watching.
    7. exit, then reboot. The relabel takes a few minutes.
    Check it
    Root can log in on the console after the reboot.

    The vSphere console types the wrong characters

    Step 3 · console · keyboard
    What you see
    A password with symbols fails in the console but works over SSH or Cockpit. Symbols come out wrong when you type visible commands.
    Why
    The console sends which key you pressed (a "scan code"), not which character you meant. If your computer's keyboard layout doesn't match what the VM expects, symbols like @ # $ | \ turn into different characters. This happens from Windows and Mac alike. Passwords are hidden, so you never see it.
    Fix
    Test the symbols (not your password) at a normal prompt: 
    bashecho '@#$\|-.'
    echo
    "Print back exactly what I typed."
    ' '
    Single quotes stop the shell from treating the symbols as special, so you see exactly what the console sent.

    Don't
    Don't type your real password on a visible command line to "see" it. It stays on the screen and in ~/.bash_history, the saved command history that auditors check.

    "Permission denied" when writing a file, even with sudo

    shell · sudo · the redirection trap
    What you see
    sudo echo "x" > /etc/file or sudo cat > /etc/file says "Permission denied."

    printf '…'
    Print text. \n means "new line," so this makes three lines.
    |
    Hand that text to the next command.
    sudo tee FILE
    tee writes what it receives into a file (and also shows it on screen). Because tee itself runs under sudo, it has permission. Add -a to add to the file instead of replacing it.

    "Kerberos authentication did not pass" or "Cannot find KDC"

    Only if the server is joined to Active Directory (not part of the base build) · SSSD · Kerberos
    Words first
    Kerberos is the ticket system Active Directory uses for logins: you prove who you are once and get a ticket (a TGT) that works for hours. The KDC is the ticket office (your domain controllers). A keytab is a file holding the server's own password, so it can get tickets without a person typing anything. SSSD is the RHEL program that talks to AD for logins.
    What you see
    AD logins or single sign-on worked, then fail, often after a long break or a network or DNS change.
    Why
    Check these in order:
    1. Clock off by more than 5 minutes. Kerberos refuses tickets from a clock that's too far off. This is the most common cause on an air-gapped server.
    2. Expired tickets. AD tickets last 10 hours by default.
    3. Can't find the ticket office. DNS isn't returning the domain controllers, or /etc/krb5.conf has the wrong realm.

    bash — on the serverchronyc tracking | grep 'System time'

dig +short -t SRV _kerberos._tcp.
    chronyc tracking | grep

    klist -kte
    List what's in the keytab: -k = keytab, -t = dates, -e = encryption types. The names it shows are the exact names to use below.
    dig
    Ask DNS a question directly (it's in the bind-utils package).
    -t SRV
    Ask for "service location" records, which say where a service lives.
    _kerberos._tcp.REALM
    "Where is the Kerberos ticket office for this realm?"
    +short
    Only print the answers. Expect one line per domain controller.
    Fix
    bash — on the serverkinit -k '$@'

    kinit -k
    "Get a fresh ticket using the keytab" instead of a typed password. Add -t FILE to use a keytab other than the default /etc/krb5.keytab.
    'SHORTHOST$@REALM'
    An AD-joined server logs in as its computer account: short name in CAPITALS, then $, then @ and the realm in CAPITALS. The single quotes stop the shell from treating $ as a variable. Copy it exactly as klist -kte showed it.
    klist
    With no options: show the tickets you now hold and when they expire.
    sss_cache -E
    Mark everything SSSD remembers (users, groups, and more) as out of date, so it asks AD again.
    systemctl restart sssd

    Restart httpd (the web server) only if the web page itself uses Kerberos logins (Satellite "external authentication"). Otherwise it's unrelated.

    klist shows a fresh ticket (krbtgt/REALM@REALM), and id <aduser> lists that user's groups.
